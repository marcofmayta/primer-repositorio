01 fundamentos

¿Qué es un Hunk?

Definición

Un hunk es un bloque contiguo de cambios dentro de un diff. Cada hunk representa una región del archivo donde hubo modificaciones, con líneas de contexto alrededor para ubicar el cambio.

¿Por qué importa?

Los hunks te permiten hacer commits quirúrgicos: agregar al stage solo partes específicas de un archivo, no el archivo completo.

Ejemplo: un archivo con 2 hunks independientes

02 anatomía

Anatomía del Diff

Pasa el cursor sobre cada parte para ver su explicación ↓

server.js — diff completo anotado
···
diff --git a/server.js b/server.js
Cabecera del diff

Indica los dos archivos comparados: a/ = versión anterior, b/ = versión nueva. En un mismo repo ambos apuntan al mismo archivo.
···
index 4a3f1b..9c82e0 100644
Línea index

Muestra los hashes SHA1 cortos de los blobs de git y el modo del archivo (100644 = archivo normal, 100755 = ejecutable).
···
--- a/server.js
--- (versión anterior)

Archivo original. Las líneas precedidas por - provienen de esta versión y serán eliminadas.
···
+++ b/server.js
+++ (versión nueva)

Archivo modificado. Las líneas con + pertenecen a esta versión y serán añadidas.
···
@@ -12,7 +12,9 @@ function startServer() {
Hunk Header (@@ ... @@)

Formato: @@ -L,S +L,S @@
-12,7 → desde línea 12, 7 líneas del original
+12,9 → desde línea 12, 9 líneas del resultado
El texto después del @@ final es el contexto funcional (nombre de función).
12
const port = process.env.PORT || 3000;
Línea de contexto

Líneas sin + ni -, presentes en ambas versiones. Proveen contexto para localizar el cambio. Por defecto git muestra 3 líneas de contexto arriba y abajo (configurable con -U n).
13
-app.listen(port);
Línea eliminada ( - )

Esta línea existe en el original pero NO en el resultado. El prefijo - la distingue. NO confundir con comentario; en diff es un marcador de eliminación.
13
+app.listen(port, () => {
14
+ console.log(`Server on port ${port}`);
15
+});
Líneas añadidas ( + )

Estas 3 líneas existen en el resultado pero NO en el original. El número de líneas añadidas menos eliminadas explica el cambio en el hunk header: +12,9 vs -12,7 (+2 líneas netas).

Crear Patches


      

        

          
Método 1: git diff → archivo

          
# Cambios no staged:
git diff > mis-cambios.patch

# Cambios staged:
git diff --staged > staged.patch

# Entre commits:
git diff HEAD~3 HEAD > feature.patch

# Solo un archivo:
git diff HEAD -- app.py > app.patch

        

        

          
Método 2: git format-patch

          
# Último commit como patch:
git format-patch -1 HEAD

# Últimos 3 commits:
git format-patch -3

# Rango de commits:
git format-patch main..feature

# Con directorio de salida:
git format-patch -3 -o ./patches/

Aplicar Patches


      

        

          

          
git apply

          
Aplica el patch como cambios en el working tree (o stage). No crea commit. Ideal para
            patches generados con git diff.

        

        

          

          
git am

          
Aplica patches en formato mbox (format-patch) creando commits con toda la metadata
            original: autor, fecha, mensaje.

Conflictos

      


      

        

          

            

              
Verificar antes de aplicar

              
git apply --check cambios.patch

            

          

          

            

              
Aplicar al working tree

              
git apply cambios.patch

            

          

          

            

              
Aplicar y añadir al stage

              
git apply --index cambios.patch
# Equivalente a: git apply + git add

            

          

          

            

              
Revertir un patch aplicado

              
git apply --reverse cambios.patch

            

          

        

      


      

        

          

            

              
Aplicar un solo patch

              
git am 0001-mi-feature.patch

            

          

          

            

              
Aplicar todos los patches de un directorio

              
git am ./patches/*.patch

            

          

          

            

              
Aplicar con three-way merge (recomendado)

              
git am -3 0001-feature.patch
# Intenta merge en conflictos en vez de fallar

            

          

          

            

              
Continuar tras resolver conflicto

              
git am --continue   # después de resolver
git am --skip        # saltar este patch
git am --abort       # cancelar todo

            

          

        

      


      

        

          
Cuando un patch no aplica limpiamente, git te avisa: error: patch failed o marca conflictos
            con <<<<<<<

        

        
# 1. Intentar con three-way merge:
git apply -3 mi.patch

# 2. Aplicar lo que se pueda, guardar rechazos en .rej:
git apply --reject mi.patch
# → Crea archivos .rej con hunks fallidos
# → Edita manualmente y aplica los .rej

# 3. Forzar aplicación ignorando espacios:
git apply --whitespace=fix mi.patch
git apply --ignore-whitespace mi.patch

# 4. Ajustar contexto reducido:
git apply -C1 mi.patch  # solo 1 línea de contexto

          Reglas para modificarlo:

══ REGLAS AL EDITAR ══
+  Para NO aplicar una línea -del: conviértela a contexto (quita el -)
+  Para NO aplicar una línea +add: elimina la línea completa del editor
  ¡No cambies líneas de contexto ni el @@ header directamente!
  Si borras una línea de contexto, ajusta el contador en @@

        

          
Este modo es poderoso para staging sub-hunk: cuando git no puede dividir automáticamente
            (s), puedes editar manualmente qué partes del hunk van al stage.

Stash selectivo por hunks

        
# Guardar en stash solo hunks seleccionados
git stash push -p
# Igual que add -p pero para stash
# Útil para "esconder temporalmente" parte del trabajo

git stash push -p -m "WIP: solo debug code"
# Con mensaje descriptivo

git stash show -p stash@{0}
# Ver el diff del stash antes de aplicarlo

git stash apply stash@{0}
# Aplicar stash sin eliminarlo de la lista

        

          
git stash push -p vs git stash -p: ambos funcionan en versiones modernas de git.
            La sintaxis push es más explícita y recomendada.

Flujo profesional completo

        

          

            
1. Codear

            → múltiples cambios mezclados
          

          

            
2. git add -p

            → stage solo lo relevante por commit
          

          

            
3. git commit

            → commit atómico, mensaje claro
          

          

            
4. git format-patch

            → exportar para review / backup
          

          

            
5. git apply --check

            → verificar en otro entorno
          

        

        
# Workflow completo en una sesión:
git add -p                        # selecciona hunks
git diff --staged                 # revisa qué vas a commitear
git commit -m "feat: add env config"
git format-patch -1 -o ./patches/ # exporta patch
git apply --check ./patches/*.patch# verifica portabilidad

Quiz Final

      

        

          
1. ¿Qué significa @@ -12,7 +12,9 @@ en un hunk header?

          

            
A Desde línea 12 del original hay 7 líneas; en el
              resultado desde línea 12 hay 9 líneas

            
B Se eliminan 12 líneas y se añaden 7 o 9 según
              el caso

            
C El archivo original tiene 12 líneas y el nuevo
              tiene 9

          

          

        

        

          
2. ¿Cuál es la diferencia principal entre git apply y git am?

          

            
A No hay diferencia, son alias

            
B git apply aplica cambios sin
              commit; git am aplica patches con metadata y crea commits

            
C git am es solo para ramas,
              git apply para tags
